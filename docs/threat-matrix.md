# AI 利用の脅威 × ユースケースマトリクス

[脅威カタログとマトリクス設計案](./threat-catalogs.md)の統合方針（4 層アプローチ）に従って作成した、Claude 利用時の脅威マトリクス本体。統合脅威リスト 22 行を 6 カテゴリに分け、3 ユースケース（チャットのみ / Claude Code 顧客資産なし / Claude Code 顧客資産あり）ごとの該当度と主な対策・出典を一覧する。

本ドキュメントは 2026-08 時点の各カタログ（[資料一覧](./threat-catalogs.md#資料一覧)）に基づく。各カタログは改訂が続いているため、更新時は最新版と突き合わせること。

## 凡例と出典 ID の読み方

該当度のセル値:

- **◎** そのユースケースの主要な脅威。対策を優先的に検討する
- **○** 条件付きで該当（構成・運用・扱うデータ次第）
- **−** そのユースケースには該当しない

## 判定の根拠

- **入力系**: 間接プロンプトインジェクションは、エージェントが外部コンテンツ（リポジトリ内ファイル、依存パッケージ、Web ページ）を自律的に読み込む Claude Code 系で `◎` になる。チャットのみでも、ユーザーが貼り付けた文書や Web 検索結果を経由して成立しうるため `−` ではなく `○`。直接プロンプトインジェクションは「利用者自身が攻撃者になる」構図のため、単独利用では脅威度が低く全ユースケース `○` に留めた。
- **実行・ツール系**: コマンド実行・ツール実行を伴わないチャットのみでは原則 `−`。Claude Code 系では実行そのものが攻撃面になるため大半が `◎`。このカテゴリの対策はサンドボックスの守備範囲と重なるため、[リスクと対策](./risks-and-mitigations.md)の該当リスクへ委譲している。MCP サーバー・プラグイン悪用のみ、チャット側でもコネクタ（外部ツール連携）を有効にすると成立するため `○` を付けた。CUA 視覚攻撃は computer use を使う構成に限られるため `○`。
- **データ・機密系**: 「機密データのプロンプト入力」はチャットのみの主戦場（`◎`）。Claude Code（顧客資産なし）では入力されるのが自社資産に限られるため `○` に下げ、顧客資産ありでは顧客情報の流出が契約問題に直結するため `◎` に戻る。認証情報の読み取り・流出はローカルファイルシステムへのアクセスがある Claude Code 系のみ該当する。
- **出力・品質系**: ハルシネーションと過度依存はどのユースケースでも発生するが、チャットのみでは出力がそのまま業務判断・文書に使われやすく `◎`、Claude Code 系では生成物がコードでありテスト・レビューという既存の検証手段が効くため `○`（ただし過度依存でレビュー自体が形骸化すると意味がないため、過度依存は全ユースケース `◎`）。バイアス・不適切コンテンツは対外向け文章・画像を作るチャット用途に固有とみなし、コード生成中心の Claude Code 系は `−` とした。
- **サプライチェーン**: slopsquatting と依存・設定の改ざんは、エージェントが依存追加・設定変更まで自律実行できる Claude Code 系に固有（`◎`）。開発時脅威（学習データポイズニング、モデル汚染）は利用者から観測も統制もできないため、統合方針の第 2 層に従い「提供者側の責任範囲」の 1 行に縮約し、対策を提供者選定に置き換えた。
- **ガバナンス・契約**: 顧客データの守秘義務は「顧客資産あり」に固有（`◎`）。著作権・ライセンスは全ユースケースで該当するが、成果物を顧客に納品する「顧客資産あり」では権利関係が契約条件になるため `◎` に格上げした。リソース消費は従量課金の API・エージェント実行を伴う Claude Code 系のみ `○`。

「チャットのみ」はコード実行を伴わないため実行系・サプライチェーンがほぼ `−` になり、かわりに入力（機密データ）と出力（ハルシネーション・過度依存・IP）が主戦場になる。「顧客資産あり」は「顧客資産なし」と技術的な脅威面は同じだが、データ・機密系とガバナンス・契約系の該当度が格上げされる。この差分が、顧客案件でサンドボックスに加えて契約・運用レイヤの対策が必須になる理由である。
