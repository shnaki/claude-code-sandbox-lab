# Claude Code のリスクと対策

Claude Code を利用するうえで発生しうるリスクを整理し、それぞれに必要な対策をまとめる。あわせて、公式が比較する 6 種のサンドボックス方式（[サンドボックス方式の比較](./sandbox-comparison.md)参照）ごとに、どのリスクを対策できるかをマトリクスで可視化する。

本ドキュメントは 2026-08 時点の公式ドキュメント（[参考リンク](#参考リンク)）に基づく。保護機構や設定は変わりうるため、実際に対策する際は最新の公式ドキュメントを確認すること。

## リスク一覧と対策

### 1. プロンプトインジェクション

- **想定シナリオ**: Web ページ、リポジトリ内のファイル、Issue 本文、MCP サーバーの応答など、信頼できないコンテンツに埋め込まれた指示を Claude が実行してしまう（間接プロンプトインジェクション）。
- **影響**: 攻撃者の意図した任意の操作（データ流出、コード改ざん、破壊的コマンド）の起点になる。後述のほぼすべてのリスクの入口。
- **対策**:
  - Manual モードの許可プロンプトで、提案されたコマンド・変更をレビューしてから承認する
  - 信頼できないコンテンツを Claude に直接パイプしない
  - `curl` / `wget` などネットワーク取得コマンドは既定で自動許可されない。完全に塞ぐ場合は `permissions.deny` に追加する
  - 外部 Web サービスとやり取りする作業は VM など強い隔離の中で行う（公式のベストプラクティス）
  - サンドボックスはインジェクションの発生自体は防げないが、成立後の被害範囲を限定する（[マトリクス](#リスク--サンドボックス方式マトリクス)参照）

### 2. 破壊的コマンドの実行

- **想定シナリオ**: 誤り・ハルシネーション・インジェクションにより、`rm -rf` やシステム設定の変更など、作業ディレクトリ外のホストを壊すコマンドが実行される。
- **影響**: ホスト OS 上のファイル・環境の破壊。
- **対策**:
  - Manual モードでは書き込みは作業ディレクトリ配下に限定され、それ以外は許可プロンプトが出る（working directory boundary）
  - サンドボックスで書き込み可能パスを OS レベルで制限する（プロンプトの誤承認があっても境界が守る）
  - 危険なコマンドパターンを `permissions.deny` で明示的に禁止する

### 3. 認証情報・機密ファイルの読み取り

- **想定シナリオ**: `~/.ssh`、`~/.aws/credentials`、`.env`、環境変数のトークン類を Claude（または実行されたコマンド）が読み取る。
- **影響**: 流出（リスク 4）と組み合わさると認証情報の窃取につながる。
- **対策**:
  - ネイティブ sandbox の既定では作業ディレクトリ外も**読み取りは可能**なため、`sandbox.credentials` や `denyRead` で機密パス・環境変数を明示的に遮断する（[設定例](./sandbox-comparison.md#settingsjson-の-sandbox-キー設定例)参照）
  - コンテナ / VM 方式ではホストの機密情報をマウントしない・環境変数で持ち込まない
  - Claude Code 自身の認証情報は macOS では Keychain、Windows / Linux ではファイルパーミッションで保護される

### 4. ネットワーク経由のデータ流出

- **想定シナリオ**: 読み取れたコード・認証情報を、外向き通信（HTTP リクエスト、DNS など）で外部に送信される。
- **影響**: ソースコード・機密情報の漏洩。
- **対策**:
  - ネットワークをデフォルト拒否 + 許可リスト方式にする（ネイティブ sandbox / srt の `allowedDomains`、Dev Container の iptables ファイアウォール、Claude Code on the web のプロキシ）
  - 許可リストには必要最小限のドメイン（`api.anthropic.com`、パッケージレジストリ等）だけを載せる
  - 公式の警告のとおり、**外向き通信を許可している限り、エージェントが読めるデータは流出しうる**。読み取り制限（リスク 3 の対策）と組み合わせる

### 5. 設定改ざんによる永続化・サンドボックス脱出

- **想定シナリオ**: `.git/hooks`、`.git/config`、`.mcp.json`、`.claude/commands`、`.claude/agents`、シェル起動ファイルなど、「次回以降に実行される」設定を書き換えられる。サンドボックス内のセッションで仕込まれたものが、次回の非サンドボックス実行やホストでの `git` 操作時に発火する。
- **影響**: サンドボックスを越えた任意コード実行の永続化。
- **対策**:
  - sandbox-runtime はこれらのパスへの書き込みを**設定なしでも自動的に拒否**する（Linux / WSL2 ではセッション中に作られたネストリポジトリは対象外という制限あり）
  - コンテナ / VM 方式でもプロジェクトをマウントしている場合はマウント内の `.git/hooks` 等に書けるため、無人実行後はセッションが書いたものをレビューする
  - `ConfigChange` フックでセッション中の設定変更を監査・ブロックする
  - managed settings で開発者側からポリシーを緩められないようにする

### 6. MCP サーバー・フックのホスト上での無制限実行

- **想定シナリオ**: ネイティブ sandbox は Bash コマンドだけを隔離するため、MCP サーバーとフックは境界の外＝ホスト上で無制限に動く。悪意ある・脆弱な MCP サーバーが起点になる。
- **影響**: サンドボックスを迂回したファイルアクセス・ネットワークアクセス。
- **対策**:
  - MCP サーバーは自作するか信頼できる提供元のものだけを使う（Anthropic は Directory 掲載前にレビューするが、セキュリティ監査はしない）
  - MCP サーバーに対してもパーミッションを設定する
  - プロセス全体を境界に入れる方式（sandbox-runtime、コンテナ、VM、Claude Code on the web）を使い、MCP サーバー・フックごと隔離する

### 7. 信頼できないコード・依存関係の実行

- **想定シナリオ**: 出所不明のリポジトリの検証、インストールスクリプトや `postinstall` を持つ依存関係の導入などで、悪意あるコードがそのまま実行される。
- **影響**: ホスト侵害・認証情報窃取。エージェント以前に、コードを動かすこと自体のリスク。
- **対策**:
  - 信頼できないリポジトリは専用 VM または Claude Code on the web で扱う（公式の推奨）
  - 初回のコードベース実行と新規 MCP サーバーには trust 確認が入る（`-p` の非対話実行では無効になる点に注意）
  - コンテナ方式を使う場合もコンテナエスケープの可能性は残るため、脅威度に応じてカーネル分離（VM）まで上げる

### 8. 許可プロンプト疲れによる誤承認

- **想定シナリオ**: 大量の許可プロンプトに慣れて内容を読まずに承認するようになり、危険な操作を見逃す。
- **影響**: 許可プロンプトという防御線の形骸化。
- **対策**:
  - 安全なコマンドをユーザー / プロジェクト / 組織単位で allowlist 化し、プロンプトを「読むべきものだけ」に減らす
  - ネイティブ sandbox の auto-allow モードで、境界内で完結するコマンドをプロンプトなしにする（境界が守るのでレビュー不要になる）
  - `/permissions` で許可設定を定期的に監査する

### 9. 無人実行（`--dangerously-skip-permissions` / auto mode）での暴走

- **想定シナリオ**: 許可プロンプトなしの無人実行で、誤った操作やインジェクション由来の操作が止まらずに実行される。
- **影響**: プロンプトで止まるはずだった操作がすべて素通しになる。
- **対策**:
  - `--dangerously-skip-permissions` は**必ずコンテナ・VM・sandbox-runtime のいずれかの中で**実行する（公式の指針）。ネイティブ sandbox 単体では Bash 以外が無防備なため不十分
  - 非 root ユーザーで実行する（Linux / macOS では root だとこのフラグは拒否される）
  - auto mode の classifier は操作単位の防御であり隔離境界ではないため、無人運用では隔離を重ねる
  - 無人実行後は、書き込み可能にしていたパスとセッションが作ったものをレビューする

### 10. プロジェクトコード自体の意図しない改変

- **想定シナリオ**: プロジェクトディレクトリは書き込み可能であることが前提のため、どの方式でもエージェントはコードを書き換えられる。バグ・バックドアの混入。
- **影響**: リポジトリ品質・サプライチェーンへの影響。
- **対策**:
  - **サンドボックスでは防げない**（書き込み可能にマウントした以上、公式の警告のとおり改変は可能）
  - コミット前の diff レビュー、Pull Request レビューを必須にする
  - `/security-review` や security guidance plugin で変更をチェックする

### 11. モデル・API へのデータ送信

- **想定シナリオ**: プロンプトと Claude が読んだファイルは、サンドボックスの有無にかかわらず Anthropic API（または設定したプロバイダ）に送信される。
- **影響**: 送信してはいけないデータ（規制対象データ等）の意図しない送信。
- **対策**:
  - **サンドボックスでは変わらない領域**。隔離は実行を制限するもので、送信内容は変えない
  - 送りたくないファイルは読ませない（`denyRead`、リポジトリから除外）
  - データの保持期間・学習利用の設定は [Data usage](https://code.claude.com/docs/en/data-usage) と Privacy 設定で管理する

## リスク × サンドボックス方式マトリクス

上記リスクを、公式が比較する 6 方式がどこまで対策できるかの一覧。凡例:

- **◎** 境界として対策できる（方式自体が防ぐ、または既定で保護される）
- **○** 部分的に緩和（設定・運用次第、またはカバー範囲が一部）
- **✕** この方式では対策にならない
- **−** サンドボックスの守備範囲外（どの方式でも別の対策が必要）

| リスク | ネイティブ sandbox<br>(sandboxed Bash tool) | sandbox-runtime<br>(`@anthropic-ai/sandbox-runtime`) | Dev Container | カスタム<br>コンテナ | 専用 VM | Claude Code<br>on the web |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1. プロンプトインジェクション | ○ | ○ | ○ | ○ | ○ | ○ |
| 2. 破壊的コマンド（ホスト破壊） | ○ | ◎ | ◎ | ◎ | ◎ | ◎ |
| 3. 認証情報・機密ファイルの読み取り | ○ | ○ | ○ | ○ | ○ | ◎ |
| 4. ネットワーク経由のデータ流出 | ○ | ◎ | ◎ | ○ | ○ | ◎ |
| 5. 設定改ざんによる永続化 | ✕ | ◎ | ○ | ○ | ○ | ◎ |
| 6. MCP サーバー・フックの無制限実行 | ✕ | ◎ | ◎ | ◎ | ◎ | ◎ |
| 7. 信頼できないコードの実行 | ○ | ○ | ○ | ○ | ◎ | ◎ |
| 8. プロンプト疲れによる誤承認 | ◎ | ○ | ○ | ○ | ○ | ○ |
| 9. 無人実行の境界 | ✕ | ◎ | ◎ | ◎ | ◎ | ◎ |
| 10. プロジェクトコードの改変 | − | − | − | − | − | ○ |
| 11. モデル・API へのデータ送信 | − | − | − | − | − | − |

判定の根拠:

- **ネイティブ sandbox**: 隔離されるのは Bash コマンドとその子プロセスのみ。MCP サーバー・フック（リスク 6）はホスト上で無制限に動くため ✕、無人実行の境界（リスク 9）としても単体では不十分（公式が明記）。破壊的コマンド（リスク 2）も Bash 以外の経路が残るため ○。一方、境界内のコマンドをプロンプトなしで安全に実行できるため、プロンプト疲れ（リスク 8）への対策としては本命。読み取りは既定でホスト全体に及ぶため、リスク 3 は `credentials` / `denyRead` の設定が前提で ○。
- **sandbox-runtime**: プロセス全体（ファイルツール・MCP サーバー・フック含む）が境界に入り、`.git/hooks` や `.mcp.json` など永続化パス（リスク 5）を設定なしでも自動拒否する。ただし Linux / WSL2 ではセッション中に作られたネストリポジトリが deny 対象外になる制限があり、beta の research preview である点も考慮する。リスク 3 は読み取り制限の設定次第で ○。
- **Dev Container / カスタムコンテナ**: ホストとの分離は◎級だが、マウントしたプロジェクト内の `.git/hooks` 等（リスク 5）には書けるため ○。ネットワーク流出（リスク 4）は Dev Container 参照実装がデフォルト拒否ファイアウォール込みなので ◎、カスタムコンテナは自前のポリシー設計次第で ○。コンテナ内に持ち込んだ認証情報は守れない（持ち込まない運用が前提で ○）。カーネルはホストと共有するため、untrusted コード（リスク 7）にはエスケープの残余リスクがある。
- **専用 VM**: 専用カーネルによる最強クラスの分離で、untrusted コードの評価（リスク 7）に公式が推奨する方式。ネットワーク・認証情報の扱いは構成次第なので ○。
- **Claude Code on the web**: Anthropic 管理の使い捨て VM + プロキシによる許可リスト強制。GitHub トークンを VM の外のプロキシが保持し、中にはスコープを絞った一時認証情報しか渡さないため、リスク 3 への固有の強みがある。変更はブランチ push 経由でしか手元に戻らないため、リスク 10 も PR レビューを挟める分 ○。
- **リスク 10・11 は原則どの方式でも守備範囲外**（公式の警告: 隔離は侵害の影響を減らすが、リスクをなくすものではない。書き込み可能なプロジェクトは改変されうるし、送信内容は隔離では変わらない）。コードレビューとデータ管理という別レイヤーの対策が必須。

## パーミッションモードとの使い分け

パーミッションモード（実行前の確認）とサンドボックス（実行後のアクセス制限）は補完関係にある。マトリクスの ◎ はあくまで「境界としての」対策可否であり、Manual モードのレビュー、deny ルール、managed settings による組織強制と重ねて使うことが前提。詳細は[サンドボックス方式の比較のパーミッションモード節](./sandbox-comparison.md#パーミッションモードとの関係)を参照。
